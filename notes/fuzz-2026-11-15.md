# Array search, 2026-11-15

## Starting point

The 2026-11-07 work (STRING profile, five reduced cases) was completed
first: its evidence lacked those five tests and predated the diagnostic
masking; all six local runtimes were rerun at the pinned revisions (see
`notes/evidence/COMMANDS.md`, refresh of 2026-11-15). No commits, pushes or
upstream issues were made.

## New profiles

- `arrays`: INT arrays `a0 : ARRAY[-2..2]` (initialised), `a1 : ARRAY[1..4]`,
  `m0 : ARRAY[0..1, 1..3]` in the program's VAR, read in expressions and
  written by assignments, also inside FOR loops. Subscripts: literals in
  range, the loop variable, `lo + ABS(e) MOD n`, or any INT expression with
  a variable; an execution reaching an out-of-range subscript is discarded.
- `array_calls`: `arrays` plus the user POUs of `calls`, with array
  elements also as F_TICK's VAR_IN_OUT and F_DM's VAR_OUTPUT. The array a
  call writes is read nowhere else in the expression, nor in the subscripts
  of the element being assigned.

`python3 -I tools/fuzz/test_gen.py` checks the array evaluator (bounds,
two dimensions, writes, element arguments) and both exclusions.

## Results (IronPLC, matiec, OpenPLC fork, STruC++, rk)

Exclusions `literal_args,case_call,mux_expr,not_expr,limit_inverted,ext_minmax`
(plus `std_formal` for `array_calls`):

- `arrays`, seeds 1-30 (6 statements) and 31-150 (9 statements, 6 seeds
  without a defined program): every program passes on all five runtimes.
- `array_calls`, seeds 1-120: STruC++ and rk pass all 120. IronPLC fails 13,
  all with P9999 on an element passed to F_TICK's VAR_IN_OUT, reduced to
  `pou/inout_array_element` (finding 29). matiec and the OpenPLC fork fail 31:
  19 with an element as a VAR_IN_OUT or VAR_OUTPUT argument (`tabledata__`,
  `table__ULINT_LITERAL`), reduced to `pou/inout_array_element` and
  `pou/output_array_element` (comparison.md matiec item 18, fork item 13);
  12 are known item 17 (a VAR_IN_OUT/VAR_OUTPUT call inside MIN/MAX/F_LIN
  arguments does not link).

A function block's output to an element (`d(x := 3, y => arr[i])`) passes
on matiec, IronPLC and STruC++, so the matiec defect is limited to the
function call wrappers.

## Reproduce

```sh
S=$(realpath ../scratch)
python3 -I tools/fuzz/run.py --profile array_calls --seeds 1-120 \
  --exclude std_formal,literal_args,case_call,mux_expr,not_expr,limit_inverted,ext_minmax \
  --out /tmp/st-array-calls \
  --ironplc-harness $PWD/harness/ironplc/target/release/iec61131-conformance-ironplc \
  --ironplcc $S/ironplc/compiler/target/release/ironplcc \
  --iec2c $S/matiec/iec2c --matiec-lib $S/matiec/lib \
  --openplc-iec2c $S/openplc/utils/matiec_src/iec2c --openplc-lib $S/openplc/utils/matiec_src/lib \
  --strucpp "node $S/strucpp/dist/node/cli.js" --runtime-include $S/strucpp/src/runtime/include \
  --rk-harness $PWD/harness/rk/target/release/iec61131-conformance-rk --rk $S/rk/target/release/rk
```

Add `array_elem_args` to the exclusions to search past the two new defects.
